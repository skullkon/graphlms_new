## Последовательность без изменения идентификаторов

Первый проход базового Go: читать основной синтаксис глав 1–9 и выполнять упражнения; iota, fallthrough, embedding, именованные возвраты и сложные замыкания можно оставить для второго чтения. Глава 10 с generics — полезное расширение, но не обязательное условие начала конкурентных задач; для статичных примеров сначала пройти локальный запуск из hello и тестирование из packages-modules. Глава 11 обеспечивает перенос практики в файлы, глава 12 проверяет готовность к конкурентному коду.

В concurrency сохранить текущий порядок книги. В первой главе сначала запуск и ожидание; детали G-M-P перечитать после каналов/select. В memory-model сначала один конкретный пример записи и close, затем список гарантий; к Mutex/atomic/Once возвращаться после глав 5–6. `scheduler-deep` оставить заключительным дополнительным чтением: он не нужен для решения первых задач.

Связывать чтение с практикой: goroutines + channels + select → 02, 03, 04, затем 01 после рекурсии; sync + memory-model + atomic → 05, 06, 07, 08; context + patterns → 09, 10, 11, 12; context + введение HTTP → 13, 14, 15; sync + patterns + небольшие алгоритмические разминки → 16–20; leaks-and-races → 22, затем 21; варианты worker pool → рекомендуемый маршрут топика 7 выше. Условие 04 нужно сначала сделать непротиворечивым технически.

## Готовые вставки: старт и переходы

### В hello перед «go run и go build»

Для примеров с кнопкой запуска установка Go не нужна. Чтобы запускать код локально и позже пользоваться тестами, установите Go по инструкции [go.dev/doc/install](https://go.dev/doc/install). Терминал — окно, в которое вводят команды. Откройте его и выполните `go version`: если версия не появилась, сначала завершите установку.

Создайте отдельную папку `go-study` и откройте терминал в ней. Сохраните первый полный пример этой главы в файл `main.go`. У файла должно быть расширение `.go`, а не `.go.txt`. В этой папке один раз выполните:

```bash
go mod init example.com/go-study
go run .
```

Первая команда создаёт файл `go.mod` с описанием проекта; подробнее он разобран в главе «Пакеты и модули». Вторая собирает и запускает все обычные Go-файлы текущего пакета. Точка означает текущую папку. Проверка: на экране появилась строка `Привет, Go!`. Для каждой новой полной программы заменяйте содержимое `main.go`: два объявления `main` в одном пакете не допускаются.

Чтобы сохранить программу в отдельный исполняемый файл, выполните `go build -o app`, затем `./app` в macOS/Linux. В Windows можно использовать `go build -o app.exe`, затем `.\app.exe`.

### В variables перед константами

Выражение вычисляет значение: `2 + 3` даёт `5`, а `age >= 18` даёт `true` или `false`. Для чисел доступны `+`, `-`, `*`, `/`; для целых чисел `%` возвращает остаток от деления. `17 / 5` равно `3`, а `17 % 5` равно `2`. Дробная часть целочисленного деления отбрасывается.

`x += 2` означает `x = x + 2`; `x++` увеличивает `x` на единицу. Для сравнения используют `==`, `!=`, `<`, `<=`, `>`, `>=`. Один знак `=` присваивает значение, два `==` сравнивают. Условия можно соединять: `age >= 18 && age <= 25` требует выполнения обоих, `age < 18 || age > 25` — хотя бы одного. `!active` меняет логическое значение на противоположное.

### В functions перед первым срезом

Дальше в примерах встречается `[]int{2, 4}` — список целых чисел, который в Go называют срезом. Квадратные скобки без числа задают тип среза, фигурные содержат значения. Индексы начинаются с нуля: `nums[0]` — первый элемент. `for i, v := range nums` перебирает элементы: `i` получает индекс, `v` — значение. Если индекс не нужен, вместо его имени пишут `_`. Подробности срезов — в главе «Коллекции»; пока достаточно этих правил.

### В memory-model перед первым close(done)

`struct{}` — структура без полей; `struct{}{}` — её значение. Такой тип удобен, когда нужно сообщить о событии без дополнительных данных. `make(chan struct{})` создаёт канал сигналов. В следующем примере мы ничего не отправляем: `close(done)` закрывает канал, а `<-done` дожидается закрытия. Если канал уже закрыт и пуст, приём завершается сразу. Полные правила close и буфера разобраны в следующей главе.

### В goroutines-intro перед «Что дальше»

Перед курсом по конкурентности проверьте, что можете самостоятельно написать функцию с параметром и результатом, пройти циклом по срезу, изменить поле структуры через метод с указателем и обработать `error`. Если какое-то действие пока не получается, вернитесь к соответствующей главе и выполните её упражнение.

Затем напишите функцию `sumAsync(nums []int) <-chan int`: она создаёт канал, запускает одну горутину, считает сумму и отправляет результат. В `main` вызовите её для `[]int{2, 4, 6}` и напечатайте принятый результат. Проверка: программа выводит `12` без `time.Sleep`. Почему `main` здесь дожидается результата? Приём из канала не завершится, пока отправитель не передаст число. Это ожидание результата; оно само по себе не подтверждает завершение любого кода, написанного после отправки.

Следующий курс требует самостоятельной практики. После глав о каналах и `select` начните с задачи 02, затем перейдите к 03 и 04. Задачу 01 с рекурсивной композицией оставьте после этой разминки. Для проверки гонок понадобится локальный Go и `go test -race`: кнопка запуска примера не заменяет этот инструмент.

## Готовая вставка: первые тесты

Место: `packages-modules.mdx`, перед «Частые ошибки».

Тест вызывает функцию с известным входом и сравнивает результат с ожидаемым. Сначала сохраните в `sum.go`:

```go
package main

func Sum(a, b int) int {
    return a + b
}
```

Рядом создайте `sum_test.go`:

```go
package main

import "testing"

func TestSum(t *testing.T) {
    got := Sum(2, 3)
    if got != 5 {
        t.Fatalf("Sum(2, 3) = %d; хотим 5", got)
    }
}
```

Суффикс `_test.go`, имя с `Test` и параметр `*testing.T` позволяют команде `go test` найти проверку. `t.Fatalf` отмечает ошибку и останавливает этот тест. Выполните `go test .`: при правильной функции появится `ok`. Замените `+` на `-` и запустите тест повторно: появится `FAIL` и сообщение с фактическим результатом. Верните `+`. Ошибка компиляции отличается от FAIL проверки: в первом случае тест вообще не начал выполняться.

Добавьте проверки `Sum(-2, 2) == 0` и `Sum(0, 7) == 7`. Когда появятся горутины с общей памятью, используйте `go test -race .`. Этот флаг ищет гонки данных в выполненных тестах; ожидаемые результаты и проверку завершения всё равно нужно задавать отдельно.

## Дополнительные мосты перед отдельными задачами

**Рекурсия перед 01.** Рекурсивная функция вызывает себя с меньшей задачей. Напишите `count(n int) int`: при `n <= 0` верните 0, иначе `1 + count(n-1)`. Для `count(3)` распишите вызовы `3 → 2 → 1 → 0` и возвраты `0 → 1 → 2 → 3`. Условие остановки обязательно. В or уменьшается число каналов, а сигнал завершения должен доходить и до вложенных горутин; одна рекурсия этого не гарантирует.

**Время перед 03.** `time.Duration` задаёт промежуток, например `500*time.Millisecond`; `time.Time` — момент, например `time.Now()`. Timer срабатывает один раз, Ticker выдаёт периодические тики. Поле `C` — канал, из которого читают наступившее событие. Reset задаёт таймеру новое ожидание, а Stop останавливает его. Остановка таймера сама по себе не завершает горутину, ожидающую его канал. Конкретные правила Reset зависят от версии Go и режима таймеров; их нужно сверить с техническим аудитом.

**HTTP перед 13.** HTTP-запрос обращается к серверу по URL. Метод GET запрашивает данные. Ответ содержит статус и тело; `resp.Body` позволяет читать байты тела и удерживает ресурс соединения, пока его не закрыли. Сначала создайте запрос с контекстом, затем выполните его через клиент, проверьте ошибку, поставьте `defer resp.Body.Close()` и прочитайте тело через `io.ReadAll`. Проверять err нужно после каждого действия, которое его возвращает. Производный timeout не может продлить уже более короткий срок родителя.

**BFS перед 20.** В графе пользователи — вершины, дружба — связи. Для графа `1→[2,3]`, `2→[4]`, `3→[4,5]`, `4→[1]` выпишите достижимые вершины по числу переходов от 1: расстояние 1 — 2 и 3; расстояние 2 — 4 и 5; новых вершин на расстоянии 3 нет. visited предотвращает повторный обход 4 и цикл обратно к 1. Сначала сделайте последовательный обход, затем обрабатывайте вершины одного уровня параллельно, ожидая весь уровень перед следующим. Включение startID и нумерацию глубины согласовать с реальными тестами.

**Очередь перед 25.** При трёх уровнях приоритета достаточно трёх срезов: q1, q2, q3. Под мьютексом добавьте задачу в нужный срез; воркер выбирает первую задачу из q3, иначе q2, иначе q1. Когда все пусты, ждите Cond в цикле. Проверьте вручную очередь `(1,A), (3,B), (2,C)`: выдача должна быть B, C, A. Heap понадобится, если число уровней заранее не ограничено.

**Порядок перед 26.** `chan (<-chan int)` переносит каналы для чтения целых чисел. Для каждой задачи создайте отдельный канал результата; в очередь их кладут в порядке входа. Работник может заполнить второй раньше первого, но коллектор сначала читает первый канал, потом второй. Это сохраняет порядок выдачи, но медленный первый результат задерживает выдачу последующих. Перед основным решением воспроизведите это для двух задач без динамического пула.

## Исходные технические противоречия — до правок

1. 01 требует срабатывания по значению, но для одного входа возвращает сам вход. Полученное значение не обязано закрывать исходный канал: исключение надо явно обозначить.
2. 04 обещает одновременно строгий high-first и отсутствие голодания при бесконечном high. Нужна выбранная политика, например квота high до одного low; описанный вложенный select сам по себе такого обещания не обеспечивает.
3. 10 и 14 называют немедленную/принудительную остановку callback без механизма принуждения. Различать отказ от новых задач, сигнал отмены, ожидание и возврат по сроку.
4. 13 говорит «не зависящий от дедлайна внешнего ctx», но предлагает WithTimeout(parent). Формулировка должна означать максимум 200ms с сохранением более ранней родительской отмены.
5. 16 смешивает token bucket и фиксированные окна; задание должно задать ёмкость и темп пополнения.
6. 20 смешивает друзей на уровне 0, уровни 0..3 и три шага; startID тоже имеет две интерпретации. Нужен единый пример с ожидаемым множеством.
7. 23/32 обещают minWorkers «в любой момент», но после Stop рабочих быть не должно. Указать, что инвариант действует в работающем пуле.
8. 27 обещает строгую границу в любую секунду при реализации обычным ticker. Согласовать наблюдаемый критерий: равномерный темп стартов или окно.
9. 28 требует кооперативный Run. 30 имеет Run func() без ctx: возврат по timeout не может гарантировать остановку произвольной зависшей функции.
10. В главах преждевременная отмена часто защищает отправку, но не приём; пример отменяемой sq в patterns всё ещё использует `for range in` без отменяемого ожидания. Для самостоятельной практики нужен корректный полный пример с обоими направлениями ожидания.

Непротиворечивый контракт — часть обучения: ученик должен иметь возможность по условию предсказать, что тестируется, а не угадывать скрытые допущения.

Существенные методические пробелы отчёта закрыты в принадлежащих агенту книгах и OUTLINE. Противоречия условий и технических формулировок задач из первоначального раздела выше переданы редактору/root и проверяются ими; этот список сохраняет состояние до исправлений, а не утверждает, что все пункты ещё актуальны. Задачи/topics имеют отдельного владельца.

Нельзя по чтению и автоматической проверке обещать, что курс понятен любому новичку. Следующая проверка качества — наблюдение за человеком без опыта, который самостоятельно выполняет упражнения и объясняет решения. Гарантии понимания и освоения профессии в дополнениях не добавлены.
