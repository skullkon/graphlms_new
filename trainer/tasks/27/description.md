# Задача 27: Конвейер с ограничением частоты (2 стадии, 50 RPS)

Реализуйте двухстадийный конвейер. Стадия 1 поставляет `userIDs`. Стадия 2
опрашивает внешний API функцией `callAPI(id)` в `workers` воркерах, но
допуски к вызовам выдаются одним общим лимитером с номинальным периодом
`time.Second/rps`.

```go
// RunRateLimited: стадия 1 даёт userIDs; стадия 2 опрашивает API в `workers`
// воркерах, но общий лимитер выдаёт разрешения с номинальным темпом rps.
func RunRateLimited(userIDs []int, workers, rps int, callAPI func(id int) string) []string
```

Требования:

- Все `userIDs` обрабатываются ровно один раз, результаты `callAPI`
  возвращаются (порядок не важен).
- Один общий источник разрешений на пул; каждый вызов ждёт разрешение.
  Это учебная модель номинального темпа, без строгой квоты фактических
  стартов в каждом скользящем окне при произвольном планировании.
- Параллелизм до `workers` одновременных вызовов `callAPI`.
- Реализовать вручную (например, `time.Ticker` как общий лимитер) без
  сторонних библиотек.

**На что смотрит интервьюер:**

- Общий на весь пул лимитер (тикер с интервалом `time.Second/rps`), который
  гейтит каждый вызов `callAPI`, а не отдельный лимит на воркера.
- Конвейер из двух стадий: раздача `userIDs` через канал и пул воркеров.
- Корректный сбор результатов без гонок (mutex или канал), завершение
  горутин; `-race` проверяет гонки данных, а не отсутствие утечек.
- Нижняя граница по времени соблюдается: `N` задач при `rps` не успевают
  выполниться быстрее, чем за `~N/rps` секунд.

`callAPI` должен в итоге возвращаться. Для положительных значений `rps`
период `time.Second/rps` должен быть ненулевым.
