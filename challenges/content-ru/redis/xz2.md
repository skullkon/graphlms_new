На этом этапе вы восстановите состояние при запуске, воспроизведя команды из файла AOF.

### Воспроизведение файла AOF

Раньше вы записывали поступающие команды в AOF. Теперь сделаете обратное: при запуске прочитаете и воспроизведёте эти команды для восстановления базы данных.

Если сервер запускается с `--appendonly yes` и каталог AOF уже существует, он должен:

1. Прочитать манифест `<dir>/<append_dir_name>/<append_file_name>.manifest`.
2. Найти запись с `type i` (инкрементальный файл).
3. Открыть этот файл и разобрать находящиеся в нём команды RESP.
4. Выполнить каждую команду так, словно её отправил клиент.

После воспроизведения база должна вернуться в состояние, которое было при исходной записи команд. Именно так Redis восстанавливает данные после перезапуска.

### Тесты

Тестирующая программа создаст каталог `<dir>/<append_dir_name>`, содержащий:

- Файл AOF `<random_file_name>.1.incr.aof` с одной командой `SET` в формате RESP.
- Манифест `<append_file_name>.manifest`, указывающий на этот файл AOF:

```
file <random_file_name>.1.incr.aof seq 1 type i
```

Она запустит вашу программу так:

```bash
$ ./your_program.sh --dir <dir> --appendonly yes --appenddirname <append_dir_name> --appendfilename <append_file_name>
```

После запуска отправит команду `GET`, чтобы проверить восстановленные данные:

```bash
$ redis-cli GET <key>
```

Будет проверено, что:

- Возвращённое `GET` значение совпадает со значением команды `SET` из файла AOF.
- Сервер прочитал файл AOF, указанный в манифесте, а не файл с жёстко заданным именем.

### Примечания

- Для определения файла воспроизведения необходимо прочитать манифест. Тест намеренно использует нестандартное имя (`<random_file_name>.1.incr.aof` вместо `<append_file_name>.1.incr.aof`), проверяя, что сервер следует манифесту.
- Файл AOF использует тот же формат RESP, который вы уже разбираете в клиентских соединениях. Можно повторно использовать существующий парсер RESP.
