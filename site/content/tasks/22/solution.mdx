## Идея решения

Исправления нужны в двух местах: воркеры пишут результаты в разные
индексы заранее выделенного среза, а промахи кеша одного ID объединяются
через запись `pending`.

## Эталон

```go
package solution

import (
	"fmt"
	"sync"
	"time"
)

// UserProfile — профиль пользователя.
type UserProfile struct {
	ID   int
	Name string
}

// UserFetcher параллельно загружает профили пользователей с кэшированием.
//
// Исправленная версия: воркеры пишут результат в предвыделённый слайс по
// своему индексу (никакого общего append → нет гонки), а кэш защищён мьютексом.
type UserFetcher struct {
	cache   map[int]UserProfile
	pending map[int]*profileCall
	mu      sync.Mutex
}

// NewUserFetcher создаёт загрузчик с пустым кэшем.
func NewUserFetcher() *UserFetcher {
	return &UserFetcher{cache: make(map[int]UserProfile), pending: make(map[int]*profileCall)}
}

// fetchFromRemoteAPI имитирует медленный HTTP-запрос и возвращает профиль.
func (uf *UserFetcher) fetchFromRemoteAPI(id int) UserProfile {
	time.Sleep(2 * time.Millisecond)
	return UserProfile{ID: id, Name: fmt.Sprintf("User%d", id)}
}

// profileCall publishes one result to all concurrent callers for the same ID.
type profileCall struct {
	done    chan struct{}
	profile UserProfile
}

func (uf *UserFetcher) getProfile(id int) UserProfile {
	uf.mu.Lock()
	if p, ok := uf.cache[id]; ok {
		uf.mu.Unlock()
		return p
	}
	if call, ok := uf.pending[id]; ok {
		uf.mu.Unlock()
		<-call.done
		return call.profile
	}
	call := &profileCall{done: make(chan struct{})}
	uf.pending[id] = call
	uf.mu.Unlock()

	p := uf.fetchFromRemoteAPI(id)
	uf.mu.Lock()
	uf.cache[id] = p
	call.profile = p
	delete(uf.pending, id)
	close(call.done)
	uf.mu.Unlock()
	return p
}

// job связывает позицию в исходном запросе с id.
type job struct {
	index int
	id    int
}

// FetchUsersData возвращает по одному профилю на каждый запрошенный id
// (повторы в запросе дают повторы в ответе), без гонок данных.
func (uf *UserFetcher) FetchUsersData(userIDs []int) []UserProfile {
	const workers = 5

	results := make([]UserProfile, len(userIDs))
	jobs := make(chan job)

	var wg sync.WaitGroup
	for w := 0; w < workers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobs {
				// Каждый воркер пишет в свой индекс — пересечений нет.
				results[j.index] = uf.getProfile(j.id)
			}
		}()
	}

	for i, id := range userIDs {
		jobs <- job{index: i, id: id}
	}
	close(jobs)

	wg.Wait()
	return results
}
```

## Почему это работает

`append` меняет общий заголовок среза и может писать в общие ячейки массива.
Фиксированный `results` не меняет заголовок: каждой позиции входа соответствует
одна запись. `WaitGroup` обеспечивает завершение записей до возврата результата.
Повторы ID сохраняются в ответе и не теряются из-за дедупликации загрузки.

Одного мьютекса вокруг `cache` недостаточно: два конкурентных промаха могут
оба выйти из лока и вызвать API. Первый вызывающий регистрирует `profileCall`
под тем же локом, под которым проверяет кеш. Следующие находят эту запись,
отпускают лок и ждут `done`. Разные ID продолжают загружаться параллельно.

Сетевой вызов выполняется вне мьютекса. Затем его результат записывается
в кеш и `call.profile`, а `done` закрывается. Закрытие канала синхронизировано
с чтением ожидающих: после `<-call.done` они видят опубликованный профиль.

Здесь имитация API всегда возвращает профиль. Для реального запроса запись
ожидания должна передавать также ошибку, поддерживать отмену и завершать
ожидающих при всех предусмотренных исходах. Без такой обработки паника
загрузчика оставит ожидающих заблокированными.

Пул ограничивает одновременную работу пятью воркерами, память результата — O(n).
