# Проверка курсов глазами начинающего студента

Дата: 30 сентября 2026 года. Позиция читателя: 18 лет, учится в университете, только начал программировать. Это экспертная симуляция последовательного чтения, а не наблюдение за реальными студентами. Все 12 глав «Основы Go» и 10 глав «Конкурентность Go» прочитаны целиком в порядке `frontmatter.order`. Прочитаны все 32 условия `site/content/tasks/*/problem.md`; для первых четырёх дополнительно прочитаны материалы перед задачей, а для 01 — подсказки, для 01–03 — стартовый код. Примеры в браузере и локальные программы в рамках этой проверки не запускались: выводы о препятствиях основаны на тексте и структуре кода.

Приоритеты: **P1** — студент не может выполнить обещанное действие либо получает ошибочную модель; **P2** — может продолжать, но вынужден угадывать или искать подготовку вне курса; **P3** — локальное улучшение закрепления. Пути ниже относительные к корню репозитория.

## Что мешает пройти курс с нуля

**P1. Нет самостоятельного первого локального запуска.** В `site/content/go-basics/book/hello.mdx`, раздел «go run и go build», предлагаются `go run .`, `go build`, `./app`. До этого не показаны установка Go, проверка `go version`, открытие терминала, создание папки и файла, переход в папку и создание модуля. `go mod init` появляется лишь в главе 11. Название исполняемого файла `app` тоже не задано командой сборки. Вопрос студента: «Куда вводить эту команду, что означает точка и откуда должен появиться app?» Нужно дать завершённый маршрут: установить Go по официальной инструкции для своей ОС; проверить версию; создать папку; сохранить показанный код в `main.go`; открыть терминал в этой папке; выполнить `go mod init example/hello`, `go run .`, `go build -o app`; показать ожидаемый вывод и отдельную команду запуска для Windows. Альтернатива для первого одиночного файла — явно `go run main.go`, с пояснением отличия от `go run .`. Это необходимо до первых рекомендаций «проверьте локально».

**P1. Между простыми программами и первой задачей нет лестницы упражнений.** Главы основ преимущественно показывают готовый код и объясняют результат; задания 01–32 посвящены конкурентности и интервью. Первая задача — variadic-функция над каналами с рекурсивной композицией и отсутствием утечек. Рекурсия не объясняется в главе «Функции». Вопрос: «Я только научился писать цикл — как мне самому придумать дерево каналов?» Нужны проверяемые упражнения до тренажёра: допечатать строку; изменить переменную; предсказать цикл; написать `add`; изменить число через указатель; посчитать частоты через map; реализовать один метод; обработать ошибку; получить один результат через канал; закрыть поток; остановить отправку через done. Затем объединить два сигнала, три сигнала и только после этого произвольное число. Не требуется удалять сложные задачи: нужен отдельный начальный маршрут и явный порог входа.

**P1. В нескольких учебных примерах обещание завершения не совпадает с кодом.** В `select.mdx` («Таймауты») после таймаута горутина остаётся на небуферизованной отправке. В `patterns.mdx` («Досрочный обрыв») `sq(ctx, in)` проверяет отмену при отправке, но не при ожидании следующего входа через `range`. В `context.mdx` («Context и graceful shutdown») `srv.Shutdown(ctx)` получает уже отменённый контекст. Вопрос: «Почему я повторил шаблон из урока, а задача требует отсутствия утечек?» Нужно объяснять обе точки ожидания — приём и отправку, отдельно дождаться завершения работников и дать shutdown новый контекст с ограниченным сроком. Эти замечания относятся к конкретным фрагментам, а не означают, что все приведённые программы всегда зависают: например, завершение `main` скрывает утечку отправителя в примере таймаута.

**P1. Объяснение гонок противоречит собственному определению.** `memory-model.mdx` определяет data race через отсутствие happens-before, а `scheduler-deep.mdx`, раздел «Почему гонки нельзя показать в браузере», говорит, что гонки возникают «только» при записи одновременно на разных ядрах. Вопрос: «Если поставить один процессор, гонки больше нет?» Требуемое пояснение: конфликтующие обращения без нужной синхронизации не становятся корректными от отсутствия физического параллелизма. Ограничение среды — отсутствие нужной диагностики и возможное скрытие проблемы, а не устранение самого дефекта программы. Следует разделить data race и наблюдаемую потерю инкремента; корректное число в выводе не доказывает отсутствия гонки.

| Утечки/гонки | Студент использует ранее созданный тест Counter, убирает защиту, читает два конфликтующих доступа и возвращает Mutex. Правильное число отдельно отвергнуто как доказательство корректности. Проверка finished имеет ограничение ожидания; таймаут не объявлен принудительной остановкой. |
| Планировщик глубже | Дополнительная глава не блокирует первые задачи. Упражнение различает живые G, выполнение Go-кода при одном P и количество M при блокирующих системных вызовах. Ответ не предлагает Gosched для исправления гонки. |

Новых **P1/P2** в этих упражнениях и готовых ответах при чтении не обнаружено. При переносе теста Counter всё ещё нужен полный пример из главы sync, но он указан как исходный материал, а файлы/импорты теста названы. Более сложное упражнение pipeline разумно расположено после каналов, select, sync и context: студент уже встречал необходимые конструкции.

Новые мосты устраняют часть прежних скрытых требований: Timer/Ticker отделены друг от друга, Stop не объявлен закрытием C; пример отсчёта простоя даёт 700 мс от старта после успешной передачи в 200 мс. HTTP объясняет GET, тело, ошибки Do/ReadAll, закрытие и более короткий срок родителя. BFS сначала предлагается сделать последовательно; visited объединяет проверку и запись. Для приоритетной очереди есть посильная альтернатива heap — три среза. Ordered связывает очередь входов и каналы отдельных результатов. В жизненном цикле разделены остановка приёма, дренаж, просьба отмены и ожидание завершения.

Методисту передано одно замечание **P3** к новой вводной goroutines: фразу «Функция перед go продолжает выполнение независимо от вызывающей» лучше заменить на «После go f() вызывающая функция продолжает выполнение, не дожидаясь f». Это позволит отличить вызывающую функцию от запускаемой без угадывания по слову «перед». Проверка новых разделов не является повторным подтверждением каждого старого абзаца и всех 32 обновлённых условий задач.


### Итоговая отметка координатора

Три уточнения P3 из повторной проверки внесены методистом и проверены координатором: hello различает объявления вне main и действия внутри неё, показывает конкретный путь cd в кавычках; упражнение goroutines точно говорит о продолжении вызывающей функции после go f(). Исходные замечания выше сохраняются как история проверки, а не как перечень открытых дефектов. Итоговые автоматические проверки и границы проверки приведены в README этого аудита.
