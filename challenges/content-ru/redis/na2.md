На этом этапе вы расширите `WAIT` для случая, когда реплики подключены и уже получили команды записи.

### `WAIT` после передачи команд

Ранее мы обработали случаи, когда:

- Реплик нет, и ведущий может вернуть `0`.
- Реплики подключены, но ещё не получали команды записи.

Теперь рассмотрим случай, когда команды записи уже переданы репликам. Смещения репликации больше не равны `0`, поэтому перед ответом ведущий должен проверить, какие реплики успешно обработали последнюю команду записи.

Для этого ведущий должен отправить репликам `REPLCONF GETACK *`, если после последнего `WAIT` остались неподтверждённые команды записи. Каждая реплика ответит своим текущим смещением (`REPLCONF ACK <offset>`).

Команда `WAIT` должна завершиться при любом из условий:

- Нужное число реплик подтвердило все предыдущие команды записи.
- Истекло время ожидания.

В обоих случаях ведущий возвращает число реплик, подтвердивших все предыдущие команды записи, в виде [целого числа RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/#integers).

### Тесты

Тестирующая программа запустит вашу программу как ведущий сервер так:

```
./your_program.sh
```

Затем запустит **несколько** реплик, которые подключатся к серверу. Каждая выполнит рукопожатие и будет ожидать пустой RDB.

Далее тест подключится к ведущему как клиент и отправит несколько команд записи вперемешку с `WAIT`:

```bash
$ redis-cli SET foo 123
$ redis-cli WAIT 1 500    # (must wait until either 1 replica has processed previous commands or 500ms have passed)

$ redis-cli SET bar 456
$ redis-cli WAIT 2 500    # (must wait until either 2 replicas have processed previous commands or 500ms have passed)
```

### Примечания

- Возвращённое количество реплик может быть меньше или больше числа, указанного в команде `WAIT`.
