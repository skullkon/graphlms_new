# Технический и редакторский аудит курсов Go — 30 сентября 2026

Проверены исходные 12 глав «Основы Go», 10 глав «Конкурентность Go», семь тематических страниц и все 32 задачи: условия, подсказки, теория, разборы, reference.go и solution_test.go. Проверка сочетала чтение, поиск повторяющихся технических утверждений, сопоставление контрактов с кодом и официальными источниками. Это не формальная верификация всех расписаний конкурентной программы. Практику и новые вводные разделы добавлял методист; их повторное чтение отражено также в отчёте ученика.

Правки сохраняют идентификаторы, порядок, сигнатуры публичных API и MDX-компоненты. Эталоны и тесты Go исправлял основной агент; этот редактор изменял текст и синхронизировал изменённые условия с trainer/tasks/*/description.md. Каталог, manifest и UI в редакторскую часть не входили. Использован навык russian-editor, без полного переписывания курса ради стиля.

## Проверки

Редактор выполнил на Go 1.25.6 darwin/arm64:

- Разбор всех 32 hints.json: синтаксис JSON корректен.
- Две отрицательные компиляционные проверки: int(19.99) отклонён как неподходящая константа, n=42 для n *int отклонён.
- Положительная проверка диагностики: несинхронизированные увеличения при GOMAXPROCS(1) всё равно обнаруживаются go run -race.
- Сверка изменённых site problem с CLI description; копии синхронизированы.

По результатам основного агента: все 98 go play примеров окончательных глав выполнились, 159 web-тестов прошли; первоначальные 32 эталона прошли -race, после исправлений основной агент также завершил финальный прогон. Исправление 01 подтверждено тестом, который проваливал исходный singleton. Исправление 16 подтверждено внедрёнными часами: исходный refill давал 7 вместо 10 допусков за 1.05s при 10rps, исправленный — 10. В задаче 19 ложная проверка «распределения» переименована в ManyKeys, в 30 порог быстрого Stop уменьшен с 5s до 500ms при timeout=100ms. Эти результаты принадлежат проверкам основного агента; полные результаты и команды финального прогона фиксируются в сводном отчёте.

## Оставшиеся ограничения API

Это явно описанные границы учебных контрактов, а не оправдание неверного эталона:

- 10: отмена не прерывает process; при двух готовых ветках select возможен дополнительный приём. Контракт требует скорой реакции, не атомарного admission.
- 15: буфер предотвращает зависание отправки, а не зависание самой функции реплики.
- 14/30: arbitrary Run нельзя принудительно завершить; после timeout функции могут продолжаться, при вечной функции её goroutine остаётся. В 14 остаётся также goroutine ожидания WaitGroup. Для полной остановки нужна кооперативная функция.
- 17: Stop прекращает выдачу, но не будит Acquire, который ждёт только gate. Условие требует закончить Acquire перед Stop. API Acquire(ctx) error — отдельное расширение.
- 21/25/28/29: Start один раз, завершение отправок до Stop, новые отправки после Stop запрещены; Once сам по себе не координирует send/close.
- 23/32: Stop не гарантирует обработку остатка внешней очереди; функции должны возвращаться; нижняя граница min снимается при завершении входа/остановке.
- 24: без читателя или достаточного буфера errs отправка ошибки блокирует воркера. Ошибки нельзя незаметно терять ради видимой скорости.
- 09/26: без API отмены потребитель обязан дочитать выход, входы — завершиться.
- 27: модель общего ticker не даёт квоту реальных стартов в каждом скользящем окне при произвольных задержках планировщика. Строгий лимит требует отдельного определения границ окна и алгоритма учёта стартов.
- 30: map ID требует уникальных ID одновременно активных задач; список — согласованный снимок, а не обещание дальнейшей судьбы функции.

Новых подтверждённых обязательных дефектов эталона внутри этих явно заданных контрактов после переданных исправлений не оставлено в списке редактора. Публичные рекомендации по производительности в курсе не подтверждались измерениями на всех платформах; поэтому гарантированные выигрыши убраны.

## Дальнейшие необязательные улучшения

Расширить тесты отрицательными lifecycle-сценариями, если расширяется сам контракт; добавить cancellable Acquire; определить panic/error policy для пользовательских callbacks и реального remote API; добавить бенчмарки RWMutex/atomic/sharding на целевой архитектуре. Нельзя объявлять чистый -race доказательством отсутствия утечек или всех логических гонок. За пределами аудита остаются фактические результаты обучения живых студентов и подтверждение качества на реальных production-нагрузках.
