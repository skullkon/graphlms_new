# Локальные лаборатории курса System Design

`stream_lab.py` требует Python 3.9+ со стандартным модулем `sqlite3`. Нет платных API, аккаунтов, Docker и сторонних пакетов. Скрипт создаёт собственный временный каталог; каждый запуск начинает новый опыт и удаляет только свои временные базы. Не передавайте ему путь к рабочей базе: такой опции здесь нет.

Из корня репозитория:

```sh
python3 tools/system-design-labs/stream_lab.py
python3 tools/system-design-labs/stream_lab.py --test
```

Первый запуск печатает JSON, второй проверяет ожидаемые результаты и завершает процесс ненулевым кодом при расхождении.

Для скачанного [комплекта лабораторий](/downloads/system-design-labs.zip) команды выполняются прямо из распакованного каталога:

```sh
python3 stream_lab.py
python3 stream_lab.py --test
python3 -m unittest -v test_cases
```

`cases.py` и `test_cases.py` содержат дополнительные модели конкурентного/idempotent ledger, отказа до commit, версии поискового представления, tombstone и проверки прав по авторитетным данным. Подробные условия кейсов — в `CASES.md`. Это также Python 3.9+ без внешних пакетов.

## SQL: снимки и два окна psql

`transactions.sql` предназначен для PostgreSQL 18 и отдельной локальной учебной базы. Сам файл выполняет только setup в новой схеме `sd_isolation_lab`; совпадение имени останавливает setup. Он не удаляет и не использует чужие объекты. Перед запуском задайте `LAB_DATABASE_URL` адресом своей учебной базы, затем:

```sh
psql "$LAB_DATABASE_URL" -f transactions.sql
```

Откройте два окна `psql` к той же базе. После setup файл содержит четыре комментированных сценария: lost update, write skew в Repeatable Read, общая guard-row в Read Committed и Serializable с повтором всей проверки. Копируйте команды по меткам SESSION A/B, останавливаясь на явных BARRIER. Не запускайте все команды последовательно в одном окне: это другой эксперимент.

Ожидаемые результаты и reset описаны в файле. SQL-файл содержит ручные сценарии. При итоговой проверке на PostgreSQL 18.6 выполнены setup, отказ повторного setup и двухсессионные истории lost update, write skew, guard и Serializable (40001). Запуск одного файла не автоматизирует эти истории. Сохраните transcript двух окон и SQLSTATE. Подробный разбор — в уроке «Изоляция»; официальный договор — [PostgreSQL 18: Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html).

## Опыт 1. Результат и подтверждение

Три события имеют значения 1, 2 и 3. Правильный итог: три SQL-эффекта, сумма 6, следующий offset 3. `early` сохраняет offset перед эффектом, затем имитирует остановку; после restart остаются два эффекта и сумма 5. `late` сохраняет эффект до offset; повтор создаёт четыре эффекта и сумму 7. `safe` атомарно сохраняет inbox и эффект, затем подтверждает offset: четыре доставки дают три эффекта и сумму 6.

Прочитайте `after_crash` прежде `after_restart`. Объясните, какое устойчивое состояние сохранилось и почему повтор начинается с этой позиции. Затем перенесите проверку inbox за пределы транзакции и придумайте конкурентное расписание. Однопоточный опыт не проверяет конкуренцию двух consumers.

## Опыт 2. Время события и пересчёт

Вход содержит события минут 0, 2, 1, повтор минуты 0, минуту 5 и опоздавшее новое событие минуты 0. Одноминутное окно закрывается, когда `window_end + grace <= max_seen_event_time`; grace равен 3. Повтор `a` подавляется; новое `e` слишком позднее. Streaming-окна: `{0:2, 1:4, 2:3, 5:7}`. Replay той же последовательности даёт тот же результат. Полный batch без политики опоздания даёт для минуты 0 значение 13.

Измените grace на 6 и предскажите результат до запуска. Переставьте новое `e` перед минутой 5: event-time остаётся тем же, но политика наблюдаемого продвижения даёт другой результат. Это сознательный учебный контракт, не обещание Kafka о watermark. Если требуется окончательная точность по всем поздним событиям, нужен correction/backfill, а не только увеличение памяти окна.

## Опыт 3. Обратное давление

Producer предлагает 100 событий в секунду, consumer обрабатывает 60, буфер вмещает 200. В дискретной модели сначала принимается пачка producer, затем обслуживается consumer. После семи тактов очередь содержит 140 записей, отклонено 140. В непрерывной модели от пустого состояния рост 40/с заполнил бы буфер примерно за 5 с. Разница связана с порядком фаз такта; не приписывайте её погрешности реального брокера.

Измените consumer на 120, затем на 0. Назовите правило успешного приёма: скрипт явно отклоняет то, что не вошло в буфер. В другом продукте можно блокировать producer или надёжно сохранять события, но память не должна расти без границы.

## Что этот опыт проверяет

Мы наблюдаем устойчивые SQL-состояния после контролируемой потери памяти обработчика. Это не тест отключения питания, полной сети Kafka, распределённых выборов, `fsync` оборудования или глобальной exactly-once доставки. SQL inbox сравнивает прежний payload в той же транзакции, что распознаёт повтор; конфликт одного ID с разным содержанием вызывает отказ. `--test` проверяет конфликт и для событий окна, и для SQL inbox: offset остаётся 0, прежний эффект со значением 99 сохраняется, новые эффекты не появляются. Соединение закрывается также при исключении. Replay пишет только вычисленный результат и не повторяет внешние уведомления.

Сопоставьте опыт с [Kafka Design](https://kafka.apache.org/41/design/design/) и [Kafka Streams: Time](https://kafka.apache.org/41/streams/core-concepts/). Скрипт — оригинальная учебная модель, а не реализация этих продуктов.
