На этом этапе вы добавите ответы реплики на команду `REPLCONF GETACK`.

### Подтверждения ACK

Обычно реплика молча обрабатывает переданные команды. Однако ведущему нужен способ проверить, что реплика синхронизирована и не отстаёт. Для этого используются подтверждения ACK.

Ведущие Redis периодически запрашивают у реплик ACK, чтобы узнать, какую часть потока репликации они обработали.

### Команда `REPLCONF GETACK`

Когда ведущему нужна информация, он отправляет:

```bash
REPLCONF GETACK *
```

Полученная репликой команда выглядит примерно так: `*3\r\n$8\r\nreplconf\r\n$6\r\ngetack\r\n$1\r\n*\r\n`. Это `["replconf", "getack", "*"]` в виде [массива RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/#arrays).

Реплика получает команду по соединению репликации, использованному для рукопожатия, и отвечает:

```bash
REPLCONF ACK <offset>
```

Смещение — количество байтов команд, обработанных репликой. Пока можно задать смещение `0`. Отслеживание и обновление смещений появятся позже.

### Тесты

Тестирующая программа запустит вашу программу так:

```
./your_program.sh --port <PORT> --replicaof "<HOST> <PORT>"
```

Как и раньше, реплика должна завершить рукопожатие с ведущим и получить пустой RDB.

Затем тест отправит реплике `REPLCONF GETACK *`.

Ожидается `REPLCONF ACK 0`, закодированный как массив RESP (`*3\r\n$8\r\nREPLCONF\r\n$3\r\nACK\r\n$1\r\n0\r\n`).

### Примечания

- После завершения рукопожатия реплика должна отвечать **только** на `REPLCONF GETACK`. Все остальные переданные команды, например `PING`, `SET` и другие, нужно читать и обрабатывать без ответа ведущему.
